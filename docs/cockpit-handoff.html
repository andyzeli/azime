Case cockpit — handoff

As of 2026-10-17. Human-readable copy of the Claude handoff memory. Design details: docs/assessment-workspace-design.html, docs/pipeline-detail.md.

Current direction

There's no stepper. Each part of the cockpit is an input:

  • Analysis holds the shared assessment: the diagnosis list and the treatment review.
  • Prep sheet is an optional printout in a modal. It isn't a workflow step.
  • Visit is where evidence is entered, during the exam or afterward.

Agreed order: 3 ✓ → 2 ✓ → 5 → 6 → 4 (UI detail last). In phase 4, keep the diagnoses above the treatment analysis (as on the current Analysis page), not the mockup’s left/right split.

Tabs after 4–6: Records · Summary · Assessment · Visit · Opinions · Report

MMI scope (decided 2026-10-18): one MMI opinion per region, covering all of that region’s supported diagnoses. Whole-person MMI is derived: an AND across the regions, dated by the latest regional MMI date, and pending while any region is pending. There are no per-diagnosis MMI opinions; this replaces the per-diagnosis proposal in exam-to-report-design-v3.html, because adjusters want one clean answer. Differences between diagnoses go in the regional rationale. Pass 4 stays regional, with no output change.

Diagnosis list

One list per case and region, in table case_region_diagnoses (migration 0014), read and saved through GET/PUT /cases/:id/diagnoses/:region. It's kept separate from steering, because steering belongs to a single 3A run.

{ canonicalDx, source: "records" | "added",
  status: "working" | "supported" | "not_supported", reason }
  • Every listed diagnosis needs a verdict. A wrong diagnosis is marked Not supported with a reason. Only diagnoses the physician added can be removed.
  • Before the first save (revision 0), the list is the 3A scope plus every records diagnosis, all set to Working.
  • Editor: components/DiagnosisList.tsx, in the Analysis setup strip. Every change saves immediately.

A diagnosis added after 3A shows an Analyze diagnosis bar above the treatments. It runs 3A for that diagnosis only and merges the result in: existing rows gain an assessment, uncovered ladder entries and AI suggestions become new rows, and a record-only row is upgraded when a ladder entry shares its episodes. Row ids and saved steering are kept. A row counts as reviewed only when every shown assessment has a decision, so rows that gained one reopen with a "new · unreviewed" tag. A new snapshot and run is still the full redo.

Prep sheet

  • Where it lives: components/ExamPrepModal.tsx. It's opened by ?prep=true in the URL, which useExamPrepModal() sets.
  • How to open it: the "Prep sheet" button at the right of the case header, or the Visit priorities header. The header button is disabled until some region has exam prep, and it shows "out of date" when the sheet is stale.
  • Toolbar:
    • the AMA mode control, which also appears in the Analysis header;
    • Update sheet, which only updates regions whose steering has been saved;
    • Print, which prints exactly what's shown, with a footer that says how current each part is.
    Opening the sheet never runs AI.
  • Analysis footer: "Save steering" is the primary button. "Update prep sheet" is secondary; it saves steering if needed and then runs 3B.
  • "Out of date" compares contents, not revision numbers. A saved edit that is later undone doesn't count. It checks:
    • the exam prep scope against the current diagnoses;
    • the steering each run used against the saved steering;
    • whether 3A has been re-run.

Fixed: 3A never got the taxonomy

queries/ladderEntries.ts matched canonical_diagnoses.label against canonical IDs, so 3A and the added-diagnosis run always received an empty ladder and every row came back as an AI suggestion. It now matches on canonical_diagnoses.id. Analyses run before the fix have no taxonomy rows; take a new snapshot and re-run 3A to get them (this resets steering).

Visit priorities: read-only

3B's visit priorities are suggestions only: at most three, each grounded in a specific conflict, kept gap or unclear finding, and often none. Nothing is recorded against them; the physician covers what matters in the note, which pass 4 reads. (Priority responses and pass 4 "clarifications" were removed.)

Phase 2 (pass 4) — built

Built directly from 3A + steering + the diagnosis list + the visit. No exam prep (3B) needed. Scope is the current diagnoses only, as in 3B: pass 4 never gives necessity opinions.

input = { caseContext, region,
          caseSummary,                                // incidentNarrative, statusTimeline, caseWideSummary, psychosocialFactors
          diagnoses: [{ canonicalDx, label }],        // supported only (none may be left Working)
          reviewedTreatmentAnalysis,                  // 3A + steering, current diagnoses; kept gaps/inconsistencies
          visit: { examinationDate,                   // visit creation date for now; later the office visit date
                   note,                              // one free-text field; pass 4 reconciles it with PDQ + AMA
                   pdq, questionnaires, amaFindings } }
output = { trajectory: { subjective, functional, objective },     // 3B's shape, computed here
           plateauEvidence: { supporting: string[], opposing: string[] },
           mmiPosture: { direction, rationale },
           unresolvedQuestions: [{ question, whyItMatters, wouldResolve }] }
basedOn = { caseSummaryId, 3A id/updatedAt, steering rev, diagnoses rev,
            visit rev, pdq id/updatedAt, questionnaire ids }
  • Not pass 4 outputs (plain queries, shown in Opinions): remaining care (applicable and not exhausted or exhaustion unclear, unclear applicability, or exhausted but ongoing) and necessity questions (treatments whose linked diagnoses are all Not supported).
  • Necessity: Not supported doesn't automatically mean "not medically necessary", because a diagnosis that has since resolved may have justified the earlier care. The physician answers necessity questions in Opinions. The reason stays optional (inferred if blank), and there's no basis field.
  • Assessment footer gets the readiness checklist and "Run post-exam analysis": 3A run, steering saved with every row reviewed, visit documented, current diagnoses all analyzed, and no diagnosis left Working (decided).
  • AMA findings are kept even when no linked diagnosis remains.
  • Prune removes the row, so use it only when the treatment didn't happen.

Phase 3 design (built)

Adding a diagnosis runs 3A for that diagnosis only. The model gets the existing rows as input, so it assesses them and doesn't suggest them again.

type PreExamDelta = {
  canonicalDx: string;                       // the added diagnosis
  existingRowAssessments: { rowId: string; assessment: TreatmentAssessment }[];
  newRows: TreatmentRow[];                   // source: "taxonomy" | "ai" only
};
Delta itemMerge
Existing rowAppend the assessment for the new diagnosis (unreviewed). Row id, prior assessments, and steering are untouched.
New taxonomy rowAdd if its treatmentId isn't present. If its episodeIds overlap a record_only row, upgrade that row instead (keep its id, set treatmentId, add the assessment), so there's no duplicate.
New ai rowAdd as a suggestion, assessed for the new diagnosis only, unreviewed. No server-side fuzzy dedupe; the prompt says not to repeat existing rows.
record_onlyNever created by a delta. Records don't change when a diagnosis is added, and the original 3A already made every non-taxonomy episode a record_only row. The only possible change is an episode gaining a taxonomy home, which is the upgrade case.

Removing a diagnosis is a filter, which already works through status. A full 3A regeneration stays a separate, explicit action.

Visit document

One JSON document per case, read and saved through GET/PUT /cases/:id/visit with expectedRevision.

{ note, pdqId, includedQuestionnaireIds, priorityResponses,
  amaHistory:     [{ region, canonicalDx, confirmed }],
  amaAssessments: [{ id, region, canonicalDxIds, rowId, nerveRoot, side,
                     answers, motorGrades, atrophyCm }] }
  • One assessment = one AMA row + the actual root + side. A bilateral finding is two assessments.
  • Diagnoses that share a component share one assessment (canonicalDxIds).
  • A missing or null answer means unresolved, never false.
  • Strength: a grade per muscle (motorGrades) derives the motor_* answers.
  • Atrophy: centimetres per measurement site (atrophyCm) derive the atrophy bands. Circumference tasks are split by site (thigh/calf, upper arm/forearm).
  • Reflex is the only check-all-that-apply section left.
  • Save validation rejects:
    • a bad root or side;
    • an unknown question or task;
    • derived answers that don't match the grades or measurements.

Post-exam snapshot

"Save & run post-exam analysis" adds a row to case_post_exam_analysis: a frozen copy of everything pass 4 will read. AI generation is still disabled (it returns 501).

  • visit.amaFindings stores each answer next to the test and question text that produced it, so the report can say what was tested.
  • It's currently built from exam prep. Phase 2 changes that (see above).

AMA

  • Reference data is maintained by the user:
    • ama_diagnostic_rows;
    • canonical_diagnoses.ama_row_ids / ama_rating_table_ids;
    • ama_rating_tables. Only the myelopathy diagnoses map to tables in v1.
    Import with pnpm --filter backend ama:import.
  • Mode is set per case (patientcase.ama_mode):
    • rating: everything;
    • guidance: rows and findings, but no rating tables;
    • off: hidden. The default is rating for work-injury cases and off otherwise.
  • Class/modifier picker (AmaClassScaleSelector): its choices are local only and not saved yet.
  • Exam prep root and table pre-selection isn't saved either, by design for now.

Pass 4 input/output design notes — 2026-10-17. Proposed shapes and prompt behavior; not implemented.

Scope: Pass 4 analyzes recovery and MMI posture for current diagnoses only. Remaining care and historical treatment-necessity questions are separate queries shown in Opinions.

Input assembly

// Pseudocode: helper names describe the required order.
const input = {
  caseContext,
  region,
  examinationDate, // actual encounter date, not documentation date
  diagnoses: currentDiagnoses, // Working / Supported, with source and status
  caseSummary,
  reviewedTreatmentAnalysis:
    projectFullReviewedAnalysis(
      scopeToCurrentDiagnoses(
        resolvePreExamReview(analysis3A, savedSteering)
      )
    ),
  visit: {
    note,
    clarifications,
    pdq,
    questionnaires,
    amaFindings,
  },
};

Resolve current saved steering, retain current diagnosis assessments, then project the full review. Include exhausted treatments, retained gaps, and inconsistencies — not just open treatment issues. No dependency on the prep snapshot or its trajectory interpretation.

Clarifications: question + response

{
  question: "Did the improvement during therapy persist afterward?",
  status: "response",
  note: "Patient reports that it lasted two weeks."
}
  • Copy the saved priority response's focus into question; include its status and note.
  • Omit not_relevant entries and 3B's whyItMatters.
  • Allow an empty array. Pass 4 needs no knowledge of pass 3, and prep remains optional.
// Prompt behavior
Check clarifications, the note, and findings before raising a question.
An answer may resolve an issue fully, partly, or not at all.
"Couldn't assess" and "declined" preserve uncertainty.
A question's wording does not establish its premise as fact.

Trajectory: computed in pass 4

Dated historical observations
  + PDQ / other questionnaires
  + today's findings and note
  → subjective, functional, objective trajectories

type Trajectory = {
  direction: "Improving" | "Stable" | "Worsening"
    | "Fluctuating" | "Insufficient Data";
  evidenceQuality: "Strong" | "Moderate" | "Sparse"
    | "Conflicting" | "Absent";
  interpretation: string;
};

Reuse the existing trajectory descriptions. Assess the three dimensions independently; distinguish change over time from disagreement between sources. A single observation or missing follow-up cannot establish stability.

Reconcile evidence without losing its origin

The visit note stays one free-text field. Pass 4 combines its information with structured evidence under these rules:

Patient-reported symptoms/function ≠ observed examination findings.
The same finding repeated in the note and AMA form counts once.
Conflicting entries remain a conflict unless the physician resolves them.
Missing answers do not mean normal findings.

Preserve AMA findings even when their diagnosis link disappears. They remain encounter evidence; their presence does not reinstate an excluded diagnosis.

Output: four groups

type Pass4Output = {
  trajectory: {
    subjective: Trajectory;
    functional: Trajectory;
    objective: Trajectory;
  };
  plateauEvidence: {
    supporting: string[];
    opposing: string[];
  };
  mmiPosture: {
    direction:
      | "Leans Toward MMI"
      | "Leans Against MMI"
      | "Indeterminate";
    rationale: string;
  };
  unresolvedQuestions: {
    question: string;
    whyItMatters: string;
    wouldResolve: string;
  }[];
};
  • wouldResolve names the specific missing information that would answer the question. It is not a requirement to perform another test.
  • Limit unresolved questions to material uncertainties affecting trajectory, plateau, or MMI interpretation. Return [] when none remain.
  • Plateau evidence statements should explain specific findings, dates, or treatment responses and their significance. Structured source references are not required; the frozen input snapshot preserves what the model received.
  • Finalize the prompt and output descriptions together.

Boundary: Pass 4 synthesizes the current clinical course, explains supporting and opposing evidence, and exposes remaining uncertainty. It does not prescribe remaining care, decide historical necessity, calculate impairment, or make the physician's final MMI determination.
